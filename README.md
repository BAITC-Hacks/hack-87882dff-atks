# SupplyMind AI

Хакатонный MVP: веб-панель менеджера, мобильные складские операции и единая MySQL-база. Интерфейс на русском, палитра: лайм и тёмно-зелёный.

```text
Web / React Native -> PHP REST API -> MySQL
                           |
                           +-> mock / Python FastAPI (контракт 1.0)
```

## Что реализовано

- Веб-панель: Обзор, Остатки, Товары, Продажи, Поставщики, Прогноз, Закупки, Заказы поставщикам, AI-агент.
- Группировка рекомендаций по поставщикам, изменение количества, отдельный экран проверки и ручное подтверждение менеджером.
- Разбор товара: остаток, поставки в пути, прогноз, восстановленный спрос, исключённые разовые продажи, дефицит, рост, сезонность, срок поставки и объяснение.
- Авторизация с ролями менеджера и сотрудника склада. Токены действуют 24 часа; в базе хранится только их хеш.
- Мобильные вкладки: Операции, Склад, История, Профиль. Камера Barcode/QR и ручной поиск по артикулу или штрихкоду.
- Приёмка, выдача, перемещение, списание и инвентаризация с журналом, транзакциями, проверкой отрицательного остатка и повторных запросов.
- Частичная и полная приёмка подтверждённого заказа: фактический остаток увеличивается, количество в пути уменьшается.

**Заказы не отправляются поставщикам автоматически.** Расчёт создаёт рекомендации, подтверждение менеджера создаёт заказ и ожидаемую поставку. Склад меняется только при физической операции.

Числовой прогноз сейчас использует явно обозначенный **mock**, а не обученную ML-модель. Подключение реального FastAPI подготовлено. **OpenAI подключён отдельно для текстового объяснения рекомендаций**, без права менять количество или подтверждать заказ. Jetson/hardware, файлы Figma и публикация в магазинах приложений в этот MVP не входят.

## Запуск на Windows

Требуются PHP 8.1+ с PDO MySQL и cURL, MySQL, Composer, Node.js, npm. Для Expo используйте версию Node, подходящую установленному SDK 57.

Создайте базу `smartstock` с кодировкой `utf8mb4` и настройте `.env` по `.env.example` (`DB_HOST`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`). Существующий `.env` не перезаписывайте.

В корне проекта:

```powershell
composer install
npm.cmd install --prefix web
php setup.php
php demo-demand.php
php -S 0.0.0.0:8000 router.php
```

`setup.php` добавляет таблицы и мигрирует старую схему, сохраняя данные. `demo-demand.php` один раз добавляет демонстрационный SKU `SM-DEMO-OAT-06`; в пустой базе также создаёт два склада и поставщика. `seed.php` относится к старому демо и запрещён после миграции, потому что очищает данные.

Веб-панель: **http://localhost:8000/manager**. Отдельный сервер для панели не нужен.

Демонстрационные учётные записи:

| Роль | Логин | Пароль |
| --- | --- | --- |
| Менеджер | `manager@supplymind.local` | `SupplyMind2026!` |
| Склад | `warehouse@supplymind.local` | `SupplyMind2026!` |

Это локальное демо. Перед внешним размещением замените демонстрационные пароли, включите HTTPS, ограничьте CORS и добавьте защиту входа от перебора. PHP development server не предназначен для production. Секреты храните только на сервере, не в Expo и не в `EXPO_PUBLIC_*`. Ранее опубликованный API-ключ нужно отозвать.

## Мобильное приложение

Во втором терминале:

```powershell
cd D:\Projects\smartstock-hackathon\smartstock-mobile
npm.cmd install
npx.cmd expo start -c
```

Запускать Expo нужно **в `smartstock-mobile`**, не в корне PHP-проекта. В браузере можно проверить формы через Expo Web; сканер камеры нужно проверить на физическом устройстве с разрешением на камеру.

По умолчанию приложение использует адрес компьютера с Metro и порт 8000. Для другого адреса задайте `EXPO_PUBLIC_API_URL=http://IP-КОМПЬЮТЕРА:8000` в `smartstock-mobile/.env.local`, затем перезапустите Metro. `localhost` на телефоне означает сам телефон.

Если телефон на мобильном интернете, а компьютер в отдельной локальной сети, адрес `192.168.*` телефонам снаружи недоступен. Для такого режима потребуются доступный HTTPS backend и доступная сборка/Metro; туннель Expo сам по себе PHP-сервер не открывает. Для демонстрации на одном компьютере достаточно веб-панели и Expo Web.

## Сценарий демонстрации

1. Войдите менеджером в веб-панель и нажмите «Рассчитать закупки».
2. Откройте «Закупки»: рекомендации сгруппированы по поставщикам. В разборе `SM-DEMO-OAT-06` видны дни дефицита и исключённая разовая продажа.
3. Измените количество, выберите позиции или нажмите «Проверить заказ» у поставщика. Подтвердите в отдельном диалоге.
4. Откройте «Заказы поставщикам». Остаток пока не изменился, появилась ожидаемая поставка.
5. В мобильном приложении войдите сотрудником склада, выберите склад и «Приёмка», введите `SM-DEMO-OAT-06` или отсканируйте его код.
6. Выберите ожидаемый заказ, укажите количество и нажмите «Провести операцию». Проверьте общие остатки и журнал.

Изменение продаж, остатка, поставщика или ожидаемых поставок после расчёта делает рекомендацию устаревшей: перед подтверждением потребуется пересчёт. Для списания и инвентаризации обязательна причина. История продаж редактируется отдельно и сама не проводит выдачу товара.

## REST API

Все маршруты ниже имеют префикс `/api/v1/`. Кроме `login`, требуется `Authorization: Bearer <token>`.

| Метод | Маршрут | Доступ / назначение |
| --- | --- | --- |
| POST | `login`, `logout` | Вход и завершение сессии |
| GET | `session`, `catalog`, `inventory` | Сессия, справочники, остатки |
| GET | `lookup?code=...` | Поиск SKU / Barcode / QR |
| GET, POST | `movements` | Журнал и складская операция |
| GET | `purchase-orders` | Подтверждённые и полученные заказы |
| GET | `workspace`, `recommendations` | Менеджер: данные панели и рекомендации |
| POST | `procurement/run` | Менеджер: выполнить расчёт |
| POST | `procurement/approve` | Менеджер: подтвердить отредактированные количества |
| POST | `products`, `suppliers`, `sales` | Менеджер: добавить товар, поставщика, исправить итог продаж за день |

Старые endpoints создания и подтверждения заказов возвращают 410. Legacy GET endpoints сохранены для совместимости складского экрана; они не создают заказы.

Пример складской операции:

```json
{"type":"receive","product_id":6,"warehouse_id":1,"quantity":10,"order_id":42,"request_id":"mobile-unique-request-123"}
```

Типы: `receive`, `issue`, `transfer`, `writeoff`, `count`. Для `transfer` требуется `destination_id`; для `count` также `expected_version` из остатков. `quantity` при инвентаризации означает фактическое количество, включая ноль. Приёмка без `order_id` не закрывает ожидаемую поставку.

Пример ручного подтверждения:

```json
{"request_id":"manager-unique-request-123","items":[{"id":1,"version":1,"quantity":120}]}
```

При повторе запроса используйте тот же `request_id` и то же тело. При потере ответа это предотвращает дублирование.

## ML-интеграция

### Новый Intelligence Service

Готовая Python-часть находится в `intelligence/`: исходники, тесты, Excel/CSV,
модель и готовые результаты из командного архива. Linux `.venv` и ключи не перенесены.
Для Windows создано отдельное окружение `.venv-intelligence`.

Первоначальная установка (на этом компьютере уже выполнена):

```powershell
python -m venv .venv-intelligence
.\.venv-intelligence\Scripts\python.exe -m pip install -r intelligence/requirements.txt
php setup.php
```

Запуск Python из корня проекта в отдельном терминале:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/start-intelligence.ps1
```

В корневом PHP `.env`: `INTELLIGENCE_API_URL=http://127.0.0.1:8004`.
PHP остаётся на `8000`, Expo на `8081` (или другом свободном порту).
Python слушает только localhost: телефон обращается к PHP, не к FastAPI напрямую.
Swagger: <http://127.0.0.1:8004/docs>.
Проверка без вызова OpenAI: `php tools/check-intelligence.php`.

Веб-разделы «Обзор», «Прогноз», «Закупки» показывают результаты Python;
в мобильном приложении добавлена вкладка «Прогнозы». Есть поиск SKU,
фильтры, подробный разбор и явное отображение отсутствующих данных.
Пересчитанный снимок содержит 422 прогноза, 21 позицию к пополнению и 25 на проверку;
интерфейс считает эти числа из API, а не хранит константы.

Интерфейсы оформлены под Qoyma с исходным `qoyma.png`, светлым фоном и синим
акцентом. Общий каталог теперь показывает 724 SKU из файлов остатков, MOQ и
товаров в пути. Все позиции имеют наименования из исходных данных; 302 позиции
без готового прогноза не скрываются и не получают выдуманные количества.
Первым открыт фильтр «Все». Поиск работает по имени, артикулу и коду.
«Остаток на [дата]» означает остаток из загруженного файла, не текущий баланс.
В веб-разделе «Товары» есть отдельные источники «Systeme Electric» и «Рабочий склад».

**Текущий режим: только просмотр.** Каталог Systeme Electric не импортируется
в MySQL, исторические остатки не заменяют реальные, заказы по этим результатам
не создаются. Поставщик, склад и срок поставки не выдумываются.
Текущие мобильные операции сохраняются в MySQL, но пока не синхронизируются
с историческими CSV Python. Кэш результатов хранится отдельно в `intelligencecache`;
при сбое сервиса последняя копия остаётся доступной с предупреждением.
Кнопка «Обновить результаты» получает существующий снимок, не обучает модель.

Маршруты и границы: [контракт интеграции](contracts/intelligence-integration.md).
`ML_API_URL` нельзя направлять на этот сервис: у него другой контракт.
С `INTELLIGENCE_API_URL` прежний локальный расчёт закупок блокируется,
чтобы демонстрационные данные не выдавались за Python.

### Объяснения OpenAI

Чат веб-панели подключён к `POST /api/v1/intelligence/agent/run` с телом
`{"message":"..."}`. Доступен только менеджеру. Python выбирает инструменты,
возвращает проверенные факты, `tools_used` и `requires_human_review`;
не утверждает заказы. Без ключа доступен явно обозначенный локальный разбор:
поиск кода/артикула, списки закупок, неполных данных и влияния поставок.
Это правила поиска по готовым данным, не ответ OpenAI.

Для OpenAI укажите новый `OPENAI_API_KEY` в `intelligence/.env` (UTF-8).
`OPENAI_MODEL=gpt-4.1-mini` необязателен. Файл перечитывается при запросе;
после изменения обновите результаты в панели, перезапуск Python не нужен.
Не помещайте ключ в Expo,
браузер, Git или URL. Ключи, опубликованные в чате или архиве, отзовите.
Старый ключ в корневом PHP `.env` игнорируется и не передаётся Python.
`agent_available` означает доступность разбора; `metadata.agent_mode` различает
`local` и `openai`. Наличие ключа не гарантирует доступ к модели/балансу.
При сбое провайдера ответ явно переключается на локальные факты.
Ключи из окружения сторонних процессов также не используются.

### Проверка ТЗ перед демонстрацией

[Текущая готовность и ограничения](docs/HACKATHON-READINESS.md).
База прогноза теперь использует подтверждённые историей поправки на stockout.
Добавлен сезонный прогноз с годовым ростом; метод выбирается по каждому SKU
по хронологическим backtest, а не один на весь ассортимент.
В разделе закупок есть CSV текущего фильтра и группа «Поставщик не указан».
Без реальных поставщиков и актуальных остатков утверждение этих заказов недоступно.

Старый `POST /api/v1/forecast/analyze` только читает ранее сохранённое объяснение
или исходный расчётный текст. `php tools/check-openai.php` больше не вызывает API.

Контракт и описание: [contracts/README.md](contracts/README.md), [JSON Schema](contracts/forecast-response.schema.json).

## Проверки

```powershell
php tests/supplymind-workflow.php
php tests/ai-explainer.php
php tests/intelligence-api.php
node tests/intelligence-ui.mjs
.\.venv-intelligence\Scripts\python.exe -m unittest discover -s intelligence/tests -v
node --check web/app.js
cd smartstock-mobile
npx.cmd tsc --noEmit
npx.cmd expo lint
npx.cmd expo export --platform all --output-dir .expo/supplymind-export
```

Интеграционный тест сам создаёт отдельную случайно названную БД `supplymind_test_*`, запускает временный PHP API и удаляет только эту базу после проверки. MySQL-пользователю нужны права CREATE/DROP DATABASE. Рабочая база не очищается. Проверяются роли, миграции, контракт, транзакции, повторные запросы, устаревшие рекомендации, группировка и полная/частичная приёмка.

Сборка и API-тесты не заменяют визуальную проверку на разных размерах экрана и сканирование камерой на реальном телефоне.
